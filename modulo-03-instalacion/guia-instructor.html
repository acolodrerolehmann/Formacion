1. Panorama general de instalación

Kubernetes se puede desplegar de muchas formas, desde un clúster local de un solo nodo para desarrollo hasta infraestructura multinodo en la nube para producción. La elección depende del caso de uso:

"No existe una única forma de instalar Kubernetes. La clave está en elegir la herramienta adecuada para el contexto: desarrollo local, CI/CD, o producción."
Contexto Necesidad Opciones típicas
Desarrollo local Pruebas rápidas, aprendizaje, desarrollo de apps Kind, Minikube, Docker Desktop, Podman Desktop
CI/CD Clusters efímeros para testing automatizado Kind, k3d
Producción on-premise Control total, bare-metal o VMs propias kubeadm, k3s, RKE2, OpenShift
Producción cloud Gestión delegada, escalabilidad, SLA AKS, EKS, GKE

2. Docker Desktop

Docker Desktop incluye un clúster Kubernetes integrado de un solo nodo que se activa desde las preferencias de la aplicación. Es la opción más sencilla para quienes ya trabajan con Docker.

Características

  • Se activa con un checkbox en Settings → Kubernetes → Enable Kubernetes
  • Usa el mismo Docker daemon para construir imágenes y desplegarlas en K8s
  • Incluye un clúster de un solo nodo con todos los componentes del control plane
  • Integra automáticamente kubectl y configura el contexto
  • Disponible para macOS, Windows y Linux

Ventajas

  • Cero configuración adicional — sólo activar el toggle
  • Las imágenes locales están disponibles inmediatamente en el clúster
  • Interfaz gráfica amigable para gestionar recursos
  • Actualización conjunta con Docker Engine

Limitaciones

  • Licencia: Requiere suscripción de pago para empresas con más de 250 empleados o más de $10M de ingresos
  • Solo permite un clúster de un solo nodo (no simula multi-nodo)
  • Consumo elevado de RAM (mínimo ~2 GB extra al activar K8s)
  • No permite configurar versiones específicas de Kubernetes fácilmente
  • No apto para CI/CD ni escenarios automatizados
Muchos alumnos ya tendrán Docker Desktop instalado. Mencionar que es una opción válida para pruebas rápidas pero que para el curso usaremos Kind por su flexibilidad con multi-nodo y reproducibilidad.

3. Podman Desktop

Podman Desktop es la alternativa open-source a Docker Desktop. Ofrece compatibilidad con contenedores OCI y tiene soporte experimental para Kubernetes a través de diferentes proveedores.

Características

  • 100% open-source (licencia Apache 2.0) — sin restricciones comerciales
  • No requiere daemon en ejecución (daemonless, rootless por defecto)
  • Soporta Kubernetes a través de extensiones: Kind, Minikube o Lima
  • Interfaz gráfica similar a Docker Desktop con panel de contenedores, pods y volúmenes
  • Compatible con el formato Docker Compose via podman-compose

Ventajas

  • Sin coste de licencia — ideal para entornos corporativos
  • Mayor seguridad por defecto (rootless containers)
  • Puede ejecutar pods nativamente (concepto más cercano a K8s)
  • CLI compatible con Docker (alias docker=podman)

Limitaciones

  • El soporte de Kubernetes es indirecto (usa Kind o Minikube por detrás)
  • Ecosistema de extensiones menos maduro que Docker Desktop
  • Algunas incompatibilidades sutiles con Docker en builds complejos
  • La experiencia varía entre plataformas (mejor en Linux, más compleja en macOS/Windows)
Podman Desktop es una buena opción para alumnos en empresas que no pueden usar Docker Desktop por licencias. Si algún alumno lo usa, puede instalar Kind dentro de Podman sin problemas.

4. Minikube

Minikube es el proyecto oficial de la comunidad Kubernetes para ejecutar un clúster local. Soporta múltiples drivers de virtualización y ofrece gran cantidad de addons integrados.

Características

  • Proyecto oficial del SIG (Special Interest Group) de Kubernetes
  • Múltiples drivers: Docker, Podman, VirtualBox, HyperKit, Hyper-V, KVM, QEMU
  • Sistema de addons integrado: dashboard, ingress, metrics-server, registry, etc.
  • Soporte multi-nodo (experimental) desde la versión 1.10+
  • Permite elegir la versión exacta de Kubernetes a desplegar

Instalación

# macOS
brew install minikube

# Linux
curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube

# Windows (con chocolatey)
choco install minikube

Uso básico

# Crear clúster
minikube start --driver=docker --kubernetes-version=v1.29.0

# Activar addons
minikube addons enable ingress
minikube addons enable metrics-server

# Dashboard web
minikube dashboard

# Parar y eliminar
minikube stop
minikube delete

Ventajas

  • El más maduro y documentado de todos los entornos locales
  • Gran cantidad de addons listos para usar
  • Soporte multiplataforma excelente
  • Comunidad activa y mantenimiento constante

Limitaciones

  • Más lento que Kind en la creación/destrucción de clústeres
  • El soporte multi-nodo es experimental y menos robusto que Kind
  • Usa más recursos que Kind (especialmente con driver de VM)
  • No tan adecuado para CI/CD por el tiempo de arranque
Minikube es la referencia histórica para K8s local. Si algún alumno pregunta por qué no lo usamos: Kind es más rápido, más ligero y soporta multi-nodo nativo con contenedores Docker como nodos.

5. Kind ⭐ Elegido para el curso

Kind (Kubernetes IN Docker) ejecuta nodos de Kubernetes como contenedores Docker. Fue diseñado originalmente para testear el propio Kubernetes y se ha convertido en la opción preferida para desarrollo local y CI/CD.

Kind es la herramienta que usaremos durante todo el curso. Permite crear clústeres multi-nodo en segundos, es extremadamente ligero y reproduce escenarios cercanos a producción sin necesidad de VMs.

¿Por qué Kind?

  • Multi-nodo real: Cada nodo es un contenedor Docker — puedes simular 1 control-plane + N workers
  • Rápido: Crear un clúster tarda ~30 segundos; destruirlo es instantáneo
  • Ligero: No usa VMs ni hipervisores — solo contenedores
  • Reproducible: Configuración declarativa en YAML, ideal para CI/CD
  • Versiones: Permite elegir la versión exacta de K8s con imágenes de nodo
  • Open source: Proyecto CNCF, sin restricciones de licencia

Instalación

# macOS / Linux con Homebrew
brew install kind

# macOS / Linux con Go
go install sigs.k8s.io/kind@v0.23.0

# Linux (binario directo)
curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.23.0/kind-linux-amd64
chmod +x ./kind
sudo mv ./kind /usr/local/bin/kind

# Windows (con chocolatey)
choco install kind

Requisitos previos

  • Docker o Podman instalado y en ejecución
  • kubectl instalado (para interactuar con el clúster)
  • Mínimo 4 GB de RAM disponible (recomendado 8 GB para multi-nodo)

Uso básico

# Crear un clúster simple (1 nodo)
kind create cluster --name mi-cluster

# Crear un clúster multi-nodo con fichero de configuración
kind create cluster --name curso-k8s --config cluster-config.yaml

# Listar clústeres
kind get clusters

# Obtener kubeconfig
kind get kubeconfig --name curso-k8s

# Cargar una imagen local al clúster (sin registry)
kind load docker-image mi-app:latest --name curso-k8s

# Eliminar un clúster
kind delete cluster --name curso-k8s

Configuración multi-nodo (ejemplo del curso)

# cluster-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    kubeadmConfigPatches:
      - |
        kind: InitConfiguration
        nodeRegistration:
          kubeletExtraArgs:
            node-labels: "ingress-ready=true"
    extraPortMappings:
      - containerPort: 80
        hostPort: 80
        protocol: TCP
      - containerPort: 443
        hostPort: 443
        protocol: TCP
  - role: worker
  - role: worker
  - role: worker

Verificación post-instalación

# Verificar que el clúster está corriendo
kubectl cluster-info --context kind-curso-k8s

# Ver los nodos
kubectl get nodes

# Resultado esperado:
# NAME                      STATUS   ROLES           AGE   VERSION
# curso-k8s-control-plane   Ready    control-plane   1m    v1.29.2
# curso-k8s-worker          Ready    <none>          1m    v1.29.2
# curso-k8s-worker2         Ready    <none>          1m    v1.29.2
# curso-k8s-worker3         Ready    <none>          1m    v1.29.2
"Kind nos permite simular un clúster de producción multi-nodo en nuestra máquina local usando solo contenedores Docker. Es la forma más eficiente de aprender Kubernetes sin necesitar infraestructura adicional."

7. Opciones de producción

Aunque el curso se centra en Kind para prácticas locales, es importante conocer las opciones que existen para llevar Kubernetes a producción. Se dividen en tres grandes categorías.

7.1 Kubernetes Vanilla (kubeadm)

La instalación "desde cero" del Kubernetes oficial usando kubeadm, la herramienta estándar para crear clústeres en bare-metal o VMs.

  • Qué es: El Kubernetes upstream sin modificaciones — exactamente lo que publica el proyecto K8s
  • Herramienta: kubeadm init + kubeadm join
  • Responsabilidad del operador: Networking (CNI), storage, ingress, certificados, upgrades
# Ejemplo simplificado de instalación con kubeadm
# En el nodo master:
sudo kubeadm init --pod-network-cidr=10.244.0.0/16

# Configurar kubectl
mkdir -p $HOME/.kube
sudo cp /etc/kubernetes/admin.conf $HOME/.kube/config

# Instalar CNI (ej: Calico)
kubectl apply -f https://docs.projectcalico.org/manifests/calico.yaml

# En cada worker:
sudo kubeadm join <master-ip>:6443 --token <token> --discovery-token-ca-cert-hash sha256:<hash>

Ventajas

  • Control total sobre cada componente
  • Sin vendor lock-in — es el K8s puro
  • Ideal para aprender los internals de Kubernetes

Desventajas

  • Complejidad operativa alta (upgrades, HA, backups de etcd)
  • No incluye nada "out of the box" — todo se configura manualmente
  • Requiere equipo dedicado para operaciones

7.2 Red Hat OpenShift

OpenShift es la distribución empresarial de Kubernetes más extendida. Añade una capa de opinión y herramientas sobre K8s vanilla orientada a seguridad y operaciones enterprise.

  • Base: Kubernetes + CRI-O + CoreOS (nodos inmutables)
  • Extras: Consola web, OAuth integrado, Source-to-Image (S2I), Operators Hub, pipelines CI/CD (Tekton), Service Mesh (Istio)
  • Variantes: OCP (autoinstalado), ROSA (AWS), ARO (Azure), OSD (dedicado)

Ventajas

  • Experiencia "baterías incluidas" — monitoring, logging, registry internos
  • Seguridad reforzada por defecto (SCCs, SELinux, no root)
  • Soporte empresarial de Red Hat
  • Actualizaciones automatizadas del clúster (OTA)

Desventajas

  • Coste de licencia significativo
  • Más restrictivo — algunos workloads necesitan adaptación
  • Curva de aprendizaje adicional sobre K8s estándar

7.3 Azure Kubernetes Service (AKS)

El servicio gestionado de Kubernetes de Microsoft Azure. El control plane es gestionado y gratuito — solo se pagan los nodos worker.

  • Control plane: Gestionado por Azure (etcd, API server, scheduler, controller-manager)
  • Integraciones: Azure AD, Azure Monitor, Azure Policy, Azure Container Registry
  • Networking: Azure CNI o kubenet, con Azure Load Balancer nativo
# Crear un clúster AKS con Azure CLI
az aks create \
  --resource-group mi-grupo \
  --name mi-cluster-aks \
  --node-count 3 \
  --node-vm-size Standard_D2s_v3 \
  --kubernetes-version 1.29.0 \
  --generate-ssh-keys

# Obtener credenciales
az aks get-credentials --resource-group mi-grupo --name mi-cluster-aks

Ventajas

  • Control plane gratuito — solo pagas los workers
  • Integración nativa con ecosistema Azure
  • Upgrades y parches del control plane automatizados
  • Autoescalado de nodos (Cluster Autoscaler + KEDA)

Desventajas

  • Vendor lock-in con servicios de Azure
  • Configuraciones de red complejas en escenarios híbridos
  • Menos flexibilidad en configuración del control plane

7.4 Amazon Elastic Kubernetes Service (EKS)

El servicio gestionado de AWS, el proveedor cloud más utilizado. Ofrece integración profunda con el ecosistema AWS (IAM, VPC, ALB, etc.).

  • Control plane: Gestionado por AWS (multi-AZ por defecto)
  • Nodos: EC2 (managed node groups, self-managed) o Fargate (serverless)
  • Networking: VPC CNI plugin (IPs de la VPC asignadas directamente a pods)
# Crear un clúster EKS con eksctl
eksctl create cluster \
  --name mi-cluster-eks \
  --version 1.29 \
  --region eu-west-1 \
  --nodegroup-name workers \
  --node-type t3.medium \
  --nodes 3

# Obtener credenciales
aws eks update-kubeconfig --name mi-cluster-eks --region eu-west-1

Ventajas

  • La mayor cuota de mercado en K8s gestionado
  • Fargate permite pods serverless (sin gestionar nodos)
  • Integración nativa con IAM para RBAC
  • Múltiples opciones de compute (EC2, Fargate, Graviton)

Desventajas

  • El control plane sí tiene coste (~$0.10/hora por clúster)
  • Configuración de networking más compleja que otros proveedores
  • Actualizaciones requieren más intervención manual
  • IAM roles para service accounts puede ser complejo

7.5 K3s — Distribución ligera para edge y on-premise

K3s es una distribución certificada de Kubernetes creada por Rancher (ahora SUSE) que empaqueta todo en un binario de ~70 MB. Ideal para edge computing, IoT, entornos con recursos limitados o instalaciones rápidas en producción.

  • Binario único: Incluye containerd, flannel, CoreDNS, Traefik y local-path-provisioner
  • Backend de datos: SQLite (por defecto), MySQL, PostgreSQL o etcd
  • Certificación: CNCF certified Kubernetes — compatible con cualquier herramienta estándar
  • ARM nativo: Funciona en Raspberry Pi y dispositivos ARM64
# Instalación del server (master)
curl -sfL https://get.k3s.io | sh -

# Unir un worker al clúster
curl -sfL https://get.k3s.io | K3S_URL=https://<server-ip>:6443 \
  K3S_TOKEN=<token> sh -

# El token está en /var/lib/rancher/k3s/server/node-token

# Verificar
sudo k3s kubectl get nodes

Ventajas

  • Instalación en 30 segundos — un solo comando
  • Consumo mínimo de recursos (~512 MB RAM para server)
  • Ideal para edge, IoT y Raspberry Pi
  • HA disponible con múltiples servers y embedded etcd
  • 100% compatible con K8s estándar (es certified)

Desventajas

  • Componentes simplificados (Traefik en lugar de nginx ingress, flannel en lugar de Calico por defecto)
  • Menos adecuado para clústeres muy grandes (100+ nodos)
  • Soporte enterprise requiere Rancher/SUSE

8. Instalación práctica de Kind

Paso 1: Verificar Docker

# Comprobar que Docker está corriendo
docker version
docker info | grep "Server Version"

Paso 2: Instalar Kind

# Opción recomendada (macOS/Linux)
brew install kind

# Verificar instalación
kind version

Paso 3: Instalar kubectl

# macOS
brew install kubectl

# Linux
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
chmod +x kubectl && sudo mv kubectl /usr/local/bin/

# Verificar
kubectl version --client

Paso 4: Crear el clúster del curso

# Crear con la configuración multi-nodo
kind create cluster --name curso-k8s --config cluster-config.yaml

# Verificar
kubectl get nodes -o wide
kubectl get pods -A

Paso 5: Verificación completa

# Desplegar un pod de prueba
kubectl run test --image=nginx --port=80
kubectl get pods -w

# Cuando esté Running, verificar acceso
kubectl port-forward pod/test 8080:80 &
curl http://localhost:8080

# Limpiar
kubectl delete pod test
Si Docker no está corriendo o no hay suficiente RAM, Kind fallará al crear el clúster. Asegurarse de que los alumnos tienen al menos 4 GB de RAM disponible y Docker activo.
Hacer esta parte como demo en vivo. Crear el clúster, mostrar los nodos como contenedores Docker (docker ps) y luego como nodos K8s (kubectl get nodes). Esto refuerza el concepto de que Kind usa contenedores como nodos.

🔑 Kubeconfig

Ubicación

Por defecto se encuentra en ~/.kube/config. Se puede sobreescribir con la variable de entorno KUBECONFIG o con el flag --kubeconfig.

Componentes del fichero

apiVersion: v1
kind: Config
current-context: kind-curso-k8s    # Contexto activo

clusters:                          # Lista de clústeres conocidos
- cluster:
    server: https://127.0.0.1:6443 # URL del API Server
    certificate-authority-data: ... # CA del clúster (base64)
  name: kind-curso-k8s

users:                             # Credenciales de autenticación
- user:
    client-certificate-data: ...   # Certificado cliente (base64)
    client-key-data: ...           # Clave privada (base64)
  name: kind-curso-k8s

contexts:                          # Combinación clúster + usuario + namespace
- context:
    cluster: kind-curso-k8s
    user: kind-curso-k8s
    namespace: default             # Namespace por defecto (opcional)
  name: kind-curso-k8s

Resumen rápido

SecciónQué define
clustersDirección del API Server + certificado CA
usersCredenciales (cert+key, token, o plugin de auth)
contextsAsocia un cluster + user + namespace
current-contextContexto que usa kubectl por defecto
Mostrar el kubeconfig real con kubectl config view. Señalar que cada vez que se crea un clúster Kind se añade automáticamente un contexto nuevo. Explicar que cambiar de clúster es simplemente kubectl config use-context <nombre>.
